Learning log — managing state across modules

The biggest challenge was sharing state between the three new modules without creating brittle prop-drilling chains. I had to properly understand React's Context API — not just copy-paste patterns, but read the docs to understand when context re-renders and when to split contexts to avoid unnecessary updates. That investigation directly improved how I structured the Goal Setting form and its connection to the Strategy Map view.

Technical decisions
Ant Design
The existing codebase already used Ant Design throughout. Staying consistent meant users got a uniform experience and I didn't introduce a second component library to maintain.
New modules felt native to the existing app. No style conflicts or bundle bloat from mixing libraries.
MySQL stored procedures
Some Growth Tracking queries joined four tables. Moving the aggregation logic into the database layer kept the Node.js controller clean and the response time acceptable.
API response stayed readable; complex join logic lived in one place — the database — rather than scattered across service files.

My first professional role. The job was implementing frontend CRUD interfaces for application modules — forms, data tables, create/edit/delete flows connected to APIs. Learning log — understanding React rendering

Early on, I was causing unnecessary re-renders on every keystroke in form components. I went back to the React documentation on controlled vs. uncontrolled components and reconciliation. Understanding that React re-renders a component tree — not just one element — changed how I thought about where to put state. I started placing state closer to where it was used and stopped lifting everything to the top. That habit has carried into every project since.

What I focused on

When I didn't understand why something behaved unexpectedly, I read the official documentation rather than just trying random fixes. Slower initially, but it built a model I could reason from.
Developed a mental model for React's component lifecycle that made debugging faster — I could predict what would happen before running code.
DRY component structure
Noticed repeated form layouts across different modules. Extracted a reusable FormField wrapper, cutting duplicated code and making future changes one-place edits.
Introduced me to the real value of abstraction: not cleverness, but reducing the number of places where a single concept lives.

How I work

Principles I actually
try to follow.

01
Read the docs first

Before copying a Stack Overflow snippet, I read the official documentation. It's slower at first, but it builds a mental model that makes me faster and more accurate over time. I'd rather understand one tool deeply than skim five tutorials.

02
DRY is a discipline, not a rule

Don't repeat yourself — not because it's a principle to follow, but because repeated code means multiple places to update when something changes. I look for duplication in my own work and refactor it, even when the deadline doesn't demand it.

03
Own what you ship

If I build it and it breaks in production, that's my bug to fix. I don't consider a feature done when the PR is merged — I consider it done when it's running cleanly in the live environment. Responsibility doesn't end at deployment.

04
Stay curious about the fundamentals

Frameworks come and go. JavaScript, HTTP, the DOM, and how browsers render pages — those stick around. I invest time understanding what's underneath the abstractions I use every day, because that's what lets me debug effectively when the abstraction leaks.
